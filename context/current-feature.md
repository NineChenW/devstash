- **2026-05-09**: Command Palette Search Fix (Substring Matching) - Quick follow-up fix on top of the just-merged global search palette. Reported issue: typing "test" returned almost every item. Root cause: cmdk's default `command-score` filter is fuzzy and scores any string where the query characters appear as a *subsequence* (in order, not consecutive) within `keywords`. Since `CommandPalette.tsx` passes `[item.title, item.typeName, item.contentPreview ?? '']` (and `contentPreview` is up to 80 chars per `PREVIEW_MAX`), the joined haystack easily contains t…e…s…t somewhere — false positives everywhere. Fix: new `src/lib/search-filter.ts::searchFilter(value, search, keywords)` does case-insensitive substring matching with multi-word AND semantics (every whitespace-separated token must appear) plus title-priority scoring (returns 2 when all tokens are inside the first keyword which is the title/name, 1 if only present elsewhere in the haystack, 0 otherwise) — cmdk preserves DB-order within equal-score buckets so title matches naturally rank above content matches. Wired in via `<Command filter={searchFilter}>` at `CommandPalette.tsx:65`. Vitest coverage: `src/lib/search-filter.test.ts` with 8 cases including a regression case asserting fuzzy subsequences are now rejected ("test" no longer matches "the slowest cat"), case-insensitivity on both sides, multi-word AND semantics, missing/empty keywords array, and the title-priority scoring contract. Suite went 9/115 → 10/123. Two pre-existing diagnostics (set-state-in-effect on the data-fetch effect in `CommandPalette.tsx`) carry over unchanged. Merged to main as part of the pagination branch — the user explicitly chose to "let it ride along on the pagination branch" rather than landing this as its own branch, so the search fix and the pagination feature share the same merge but are split into two focused commits (`fix: tighten command palette search to substring matching` and `feat: paginate /items/[type], /collections, and /collections/[id]`). Heads-up: kept the strict-substring approach over reintroducing a weighted fuzzy score because the demo dataset's content/preview is dense — even a 0.5-threshold cutoff on cmdk's scorer would still bleed into noise.

- **2026-05-09**: Pagination - Server-side paginated all three listing surfaces (`/items/[type]`, `/collections`, `/collections/[id]`) and applied the dashboard limit constants. Same module exports four pure utilities, all unit-tested: `parsePageParam(raw)` reads `?page=N` from Next.js's `searchParams` (handles `string | string[] | undefined`, falls back to 1 on missing/invalid/zero/negative), `totalPages(total, perPage)` (always ≥1 even when total=0, used by the component to decide whether to render at all), `paginationWindow(current, total, siblings=1)` returns a `(number | 'ellipsis')[]` row of page tokens with the inline-vs-ellipsis rule (gap of exactly 1 between visible pages → emit the missing page rather than an ellipsis; gap ≥2 → ellipsis) and out-of-range `current` clamping, and `buildPageHref(basePath, page)` strips `?page=` for page ≤1 and sets it otherwise while preserving any other query params on `basePath` (uses `new URL(basePath, 'http://x')` for parsing — the dummy origin is required because `URL` rejects relative paths but the result is reassembled from `pathname + search` so the dummy never leaks).
